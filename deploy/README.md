# Два VPS: российский вход и зарубежный выход

Первая версия автоматизации добавляет UDP-ретранслятор перед **уже работающими**
AmneziaWG и ботом. С чистого зарубежного VPS AmneziaVPN этот скрипт не устанавливает.

```text
Клиент AmneziaWG
    │ зашифрованные UDP-пакеты, Endpoint = российский IP
    ▼
Российский VPS: nftables DNAT + SNAT
    │ те же зашифрованные пакеты
    ▼
Зарубежный VPS: существующий контейнер amnezia-awg + бот
    │ расшифровка VPN, существующий NAT Amnezia
    ▼
Интернет: сайты видят зарубежный выходной IP
```

Российский сервер не хранит ключи AmneziaWG и не расшифровывает пользовательский
трафик. Дополнительный WireGuard-туннель между VPS не нужен: пакеты уже зашифрованы
AmneziaWG. Вся маршрутизация сайтов, включая российские, остаётся через зарубежный
выход. Это простой relay, а не каскад с разделением сайтов по странам.

## Требования

**На компьютере, с которого разворачиваем:** Node.js 18+, OpenSSH `ssh` в PATH.
Подходят Windows, Linux и macOS; дополнительные npm-зависимости для deploy не нужны.
SSH должен работать по ключу/через ssh-agent без запроса пароля. Используется root.

**Вход:** выделенный Debian/Ubuntu VPS с systemd, `iproute2`, доступом к apt и
публичным IPv4 непосредственно на интерфейсе. Не поддерживаются cloud NAT,
действующий Docker, другой firewall или уже настроенная маршрутизация.
Проверка отклоняет такие хосты, вместо перезаписи чужой конфигурации.
Порт `entry.port/udp` должен быть свободен. Российский адрес выбирается при покупке
VPS: скрипт не проверяет геолокацию IP.

**Выход:** уже работающий AmneziaWG в Docker bridge, опубликованный IPv4 UDP-порт,
Node.js 18+, установленный бот из текущей версии репозитория и его npm-зависимости.
Сервис бота должен быть настроен как в основном README: `WorkingDirectory` равен
`exit.botDir`, единственный `EnvironmentFile` — `<exit.botDir>/.env`.
`exit.container` должен совпадать с `CONTAINER` в `.env`.

При подготовке обоих VPS проверь firewall в панели хостера:

- вход: доступен SSH и входящий `entry.port/udp` от клиентов;
- вход: разрешён исходящий UDP к зарубежному VPS;
- выход: опубликованный порт AmneziaWG доступен с российского VPS;
- для существующих прямых профилей сохрани прежние разрешения выхода.

Скрипт не управляет firewall хостера и не может доказать UDP-доступность без
настоящего клиентского handshake. TCP-доступность по SSH этого не подтверждает.

## Быстрый запуск

Обнови код бота на зарубежном VPS до этой версии обычным способом. Она добавляет
поддержку `ENDPOINT_PORT`, сохраняя поведение старых односерверных конфигураций.
Не создавай клиентов одновременно с перезапуском бота при развёртывании.

1. Скопируй пример локально:

   ```powershell
   Copy-Item deploy/two-vps.example.json deploy/two-vps.json
   ```

   Linux/macOS: `cp deploy/two-vps.example.json deploy/two-vps.json`.

2. Укажи два настоящих адреса и путь к боту:

   ```json
   {
     "entry": { "host": "203.0.113.10", "sshPort": 22, "port": 51820 },
     "exit": {
       "host": "198.51.100.20",
       "sshPort": 22,
       "container": "amnezia-awg",
       "botDir": "/root/amnezia-bot",
       "botService": "amnezia-bot.service"
     }
   }
   ```

   Адреса в примере документационные. Inventory не содержит токенов или приватных
   ключей и исключён из git. На обоих VPS используются те ключи, которые уже доступны
   OpenSSH через ssh-agent или `~/.ssh/config`.

3. Подключись к каждому серверу вручную и проверь SSH fingerprint по данным хостера:

   ```text
   ssh root@АДРЕС_ВХОДА
   ssh root@АДРЕС_ВЫХОДА
   ```

   Для нестандартного SSH-порта добавь `-p`. Deploy использует
   `StrictHostKeyChecking=yes` и не принимает неизвестные ключи автоматически.

4. Посмотри план и примени:

   ```text
   npm run deploy:two-vps
   npm run deploy:two-vps -- --apply
   npm run deploy:two-vps -- --check
   ```

   **В PowerShell с запретом `.ps1` используй `npm.cmd` вместо `npm`.**
   Альтернатива без npm: `node deploy/two-vps.js --apply`.

   Другой inventory: `npm run deploy:two-vps -- deploy/other.json --apply`.
   Без `--apply` выполняется только локальный план, без SSH и изменений.

После подготовки серверов и inventory для последующих установок достаточно одной
команды `--apply`. Время зависит главным образом от загрузки apt-пакетов на входе.

## Что делает apply

1. Проверяет зарубежный сервис, контейнер, `ListenPort` и Docker port mapping.
   Например, для `42000:51820/udp` relay направляет пакеты на **42000**, а не 51820.
   Закрытые ключи AmneziaWG и токен бота не выводятся и не копируются на вход.
2. Проверяет совместимость российского VPS до изменения его настроек.
3. Ставит на входе `nftables` и `conntrack`, создаёт собственную таблицу
   `ip pepa_relay`, файлы `/etc/pepa-relay/` и `pepa-relay.service` с автозапуском.
   Автозапуск стандартного `nftables.service` отключён: правилами управляет только
   `pepa-relay.service`, чтобы загрузка `/etc/nftables.conf` не стирала таблицу relay.
4. Разрешает пересылку только фиксированного UDP-потока вход → выход, его ответов
   и связанных ICMP-ошибок (в том числе для определения MTU пути).
   Остальной IPv4 FORWARD запрещён на выделенном входе. SSH/INPUT и default route
   не меняются; глобальный `flush ruleset` не используется.
5. На выходе сохраняет прежние строки `ENDPOINT_HOST/PORT` в
   `<botDir>/.two-vps-state.json`, обновляет только эти поля `.env` и перезапускает бот.
   Прочие переменные и клиентские ключи сохраняются. `.env` и state имеют права 0600.
6. Если после изменения `.env` бот не запускается, возвращает прежний `.env` и пытается
   запустить прежнюю конфигурацию. При ошибке возвращается ненулевой код.

Деплой не атомарен между двумя машинами: если настройка входа уже закончилась,
а SSH к выходу оборвался, relay может остаться установленным со старым endpoint бота.
Повтори `--apply` после устранения ошибки или используй `--rollback`.
Повторный apply не создаёт пользователей и не меняет их ключи, но обновляет правила
и очищает conntrack для endpoint; текущие клиенты могут кратковременно переподключиться.
Если `ENDPOINT_HOST/PORT` меняли вручную после deploy, автоматизация остановится,
чтобы не затереть изменения. Согласуй эти поля с сохранённым state перед повтором.

## Что получают клиенты

Новые `/add` выдают `.conf`, QR и `vpn://` с российским адресом и `entry.port`.
Публичный порт не обязан совпадать с портом внутри AmneziaWG.

**Уже импортированные профили не обновляются автоматически.** В существующем
клиентском `.conf` нужно заменить только `Endpoint` на российский IP и порт,
сохранив ключи и параметры обфускации, затем импортировать изменённый профиль.
Для `vpn://` нужен обновлённый профиль; автоматического переиздания существующих
ссылок в этой версии нет. Можно выдать новый профиль через `/add`, но это создаст
нового peer; старый сам не удалится.

Первым перенеси один тестовый клиент. До проверки новых подключений оставь рабочие
прямые профили. Смена `.env` не отключает старые peer и не закрывает публичный порт
зарубежного AmneziaWG.

## Проверка после развёртывания

`--check` проверяет сервисы, настройки endpoint, сохранённые правила и основные
параметры активной nftables-таблицы. Он **не** доказывает работоспособность VPN.

Проверь с реального устройства:

1. Подключение по новому профилю устанавливается, handshake обновляется.
2. Сервис определения IP показывает зарубежный выход; российский IP не появляется.
3. Работают DNS, IPv4, большие загрузки и звонки. Проверь IPv6 отдельно: если VPN
   его не поддерживает, клиент должен блокировать обход туннеля. Relay не меняет
   существующую IPv6-конфигурацию Amnezia и клиентский kill switch.
4. В согласованное окно недоступности останови relay и проверь отсутствие обхода
   через обычное соединение клиента. Для этого нужен kill switch в приложении.
   Relay не умеет расшифровывать пакеты и сам не может выпустить их как обычный
   пользовательский трафик с российского IP.
5. После перезагрузки входа и выхода повтори проверку подключения и внешнего IP.

Диагностика на входе:

```bash
systemctl status pepa-relay.service
journalctl -u pepa-relay.service -n 50
nft list table ip pepa_relay
```

Счётчики NAT отражают создание соединений; для проходящего трафика смотри также
счётчики цепочки `forward`. Не выводи публично полные VPN-конфиги или `.env`.

## Откат

```text
npm run deploy:two-vps -- --rollback
```

Сначала восстанавливаются прежние `ENDPOINT_HOST/PORT` и перезапускается бот.
Затем отключается service relay, удаляется только его nftables-таблица и
восстанавливается прежнее значение IPv4 forwarding. Конфиги на входе остаются
в `/etc/pepa-relay/` для диагностики; пакеты apt не удаляются.
Если восстановление бота не удалось, relay не отключается.

Откат не переписывает профили на устройствах. Клиентам, уже переключённым на
российский адрес, потребуется вернуть прежний endpoint. Если одна машина недоступна,
её часть отката нужно выполнить после восстановления доступа. Для аварийного
отключения только входа: `systemctl stop pepa-relay.service` на российском VPS.

## Ограничения этой схемы

- Российский провайдер пользователя видит российский endpoint, сайты — зарубежный
  выход. Сам факт VPN может по-прежнему определяться по трафику.
- Российский VPS должен иметь рабочий доступ к зарубежному AmneziaWG. Если зарубежный
  IP или AmneziaWG блокируется на участке Россия → выход, relay этого не обходит.
  Уже заблокированный из России адрес выхода для такой схемы может не подойти.
- Российские сайты также видят зарубежный IP. Разделение сайтов, Xray, балансировка
  и резервный выход в эту версию не входят.
- VPN завершается на зарубежном узле. Чтобы заменить этот VPS без новых клиентских
  ключей, нужно перенести серверные ключи, peer, параметры AWG и clientsTable.
  Relay не делает произвольный новый VPN-сервер взаимозаменяемым со старым.
- Автоматизация рассчитана на отдельный IPv4 relay с простым firewall. Общие серверы,
  IPv6 endpoint, Docker host networking и нестандартные установки требуют адаптации.

## Проверки разработчика

```text
npm test
npm run check
bash -n deploy/remote/entry.sh
```

Есть отдельный интеграционный тест настоящего DNAT/SNAT и обратного пути:

```bash
sudo bash test/relay-netns.sh
```

Он требует Linux, root, `ip`, `nft`, `python3`, Node.js и поддержку network namespaces.
Создаёт три изолированных namespace (клиент, вход, выход), проверяет UDP forwarding,
SNAT, запрет посторонней пересылки, повторное применение правил и отказ выхода.
Firewall и forwarding основного namespace хоста не меняет; временные namespace удаляет.
Это проверка сетевых правил, а не совместимости конкретной версии приложения Amnezia.
